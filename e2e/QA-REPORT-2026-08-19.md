# Whole-project QA report

**Date:** 2026-08-19  
**Scope:** Current working tree in `dataroom/`  
**Reference requirements:** `../ProjectDesc/` and `../ProjectPlan/`  
**Overall verdict:** **FAIL — not release-ready against the full brief**

The implemented local product is substantially complete and its core automated quality gates are green. The release verdict is still fail because the brief requires a publicly deployed frontend and backend, the repository has no deployed URL or deployment credentials/evidence, CI does not run the required E2E suite, and the storage-enabled browser acceptance path cannot currently complete cleanly. Live storage uploads themselves worked, including a 4 MiB browser upload with a native XHR progress event, but the official storage E2E tests contain two stale selectors and live PDF page rendering did not complete in the final diagnostic.

## Release blockers

### QA-B01 — Required public deployment is absent

**Severity:** Blocker  
**Requirement:** Publicly deployed frontend and backend with production Google authentication.

`README.md` explicitly records that no public deployment has been made. `render.yaml`, `vercel.json`, and `apps/api/Dockerfile` are present and the Docker image boots successfully, but this proves deployability only—not an actual deployment. No Render or Vercel credentials were available in the environment, so QA could not create or inspect a live release.

Consequently, the following production-boundary requirements remain unverified:

- public frontend and API reachability;
- Google OAuth redirect/callback using production redirect URIs;
- cross-origin refresh-cookie behavior with `SameSite=None; Secure`;
- production CORS allowlisting;
- raw browser PUTs from the deployed web origin to object storage;
- post-deploy migration and health checks.

**Required closure:** Deploy both services, configure production secrets and OAuth/storage allowlists, then run the full E2E suite and manual OAuth smoke test against the public URLs.

### QA-B02 — Storage-enabled E2E acceptance suite has two broken selectors

**Severity:** High  
**Files:** `support/selectors.ts`, `specs/02-uploads-and-viewer.spec.ts`

With `E2E_STORAGE_READY=true`, the four storage-gated tests produced **2 passed and 2 failed**. Both failures occurred after the associated product behavior appeared on screen:

1. The three-PDF test expects `ui.uploadItems` to have count 3. Its fallback locator matches `%|uploading|done`, while the actual completed queue text is **Uploaded**. Fast uploads therefore disappear from that locator even though all three queue entries and all three file rows are present. The test fails before its viewer/download assertions.
2. The unsupported-preview test successfully uploaded the text file and rendered the `UnsupportedPreview` state. `ui.downloadButton` then resolves both the toolbar Download button and the unsupported-preview CTA, causing Playwright strict-mode failure.

These are test-harness defects, not evidence that the observed upload or fallback UI failed. They still block the SPEC-10 acceptance condition because the official suite cannot finish green when storage is enabled.

**Required closure:** Scope upload items to the upload region and match the actual completed label; scope the unsupported-preview download assertion to its state container or select one deliberate button. Re-run all 44 E2E tests with storage enabled.

### QA-B03 — Live PDF page rendering remains unresolved

**Severity:** High  
**Requirement:** View an uploaded PDF in-app.

A separate live-storage diagnostic uploaded a generated 4 MiB PDF, observed a qualifying native `xhr.upload` progress event, and reached the React PDF document shell. The first `.react-pdf__Page` did not become visible within 30 seconds, so the diagnostic timed out before the download check. The official three-PDF E2E test could not reach its small-PDF viewer assertion because QA-B02 fails earlier.

Component and API tests cover viewer UI and signed-content redirects, but they do not close this real browser + object store + PDF.js path. This result is insufficient to classify the cause as a product defect—the diagnostic artifact/timeout also needs to be ruled out—but the required feature is not release-verified.

**Required closure:** Fix QA-B02 and rerun the official test, which views the small `beta.pdf`; if it still fails, collect browser console/network traces and PDF.js error output.

### QA-B04 — CI does not execute the required E2E graph

**Severity:** High  
**Requirement:** SPEC-10 requires the critical E2E flows in the delivery graph.

The repository's CI configuration runs install/static/test/build checks but no browser E2E job. A regression in deployed cookies, object-storage CORS, signed redirects, or share revocation can therefore merge while CI stays green.

**Required closure:** Add a protected environment-backed E2E job, require all storage flows, and retain Playwright traces/screenshots on failure.

## Functional and specification findings

### QA-F01 — Refresh replay behavior differs from the written SPEC-02 promise

**Severity:** Medium  
**Status:** Open product decision (`CCP-6`)

SPEC-02 states that reuse of any rotated refresh token invalidates the entire token family. The implementation provides a 15-second replay grace window for parallel refreshes. The behavior is tested and appears intentional, but it is a contract mismatch until the written requirement is changed or the grace window is removed.

**Risk:** A stolen just-rotated predecessor remains usable during the grace window; conversely, removing grace may reintroduce multi-tab refresh races.

### QA-F02 — Permissioned whole-share revocation UX is unresolved

**Severity:** Medium  
**Status:** Open product decision (`DEC-1`)

The backend supports revoking an entire permissioned share and the UI supports per-recipient removal. The plan still leaves a choice between whole-share and recipient-only revocation UX. The brief says the owner can revoke a share; current UI satisfies recipient revocation but does not expose an explicit whole-permissioned-share action.

**Required closure:** Settle the requirement and either document recipient-only behavior or add the whole-share control and acceptance coverage.

### QA-F03 — README E2E command can target a different database than the running API

**Severity:** Low  
**File:** `README.md`

The documented local E2E command hardcodes a local PostgreSQL URL. In this workspace the API was configured to a different PostgreSQL database. Running the command verbatim inserted Playwright refresh sessions into the local database while the API read the configured database, producing 15 misleading login failures. Pointing both processes at the same database yielded 40 passed / 4 storage-gated skips.

**Required closure:** State explicitly that `DATABASE_URL` for the harness must be identical to the API's database, or derive both from the same environment file.

### QA-F04 — Production web bundle exceeds Vite's default chunk advisory

**Severity:** Low

The web build passed, but Vite reported a 516.17 kB minified main JavaScript chunk (156.46 kB gzip), plus a 372.90 kB PDF chunk and a 1.37 MB PDF worker. This is not a correctness failure, but route-level/code splitting should be considered before scale testing.

### QA-F05 — Project status documentation trails the current implementation

**Severity:** Low

Some project status/handoff documents refer to an earlier commit and still describe live storage as unavailable, although this environment now has working storage credentials and deployment scaffolding was added later. Stale status records increase the chance that release work or QA coverage is misclassified.

## Security findings

These issues were reproduced or confirmed by source/configuration review. They are also consistent with the repository's existing `SECURITY-REVIEW.md`.

### QA-S01 — Proxy-aware IP handling is not enabled

**Severity:** Medium

The API does not configure Express `trust proxy`. Behind Render or another reverse proxy, the public-share rate limiter may see the proxy address instead of the client, collapsing unrelated users into one bucket and enabling a low-cost denial of service.

### QA-S02 — Anonymous/cookie authentication endpoints lack a general rate limit

**Severity:** Medium

Rate limiting is applied to public share resolution, but other anonymous and cookie-auth endpoints do not have an equivalent global/auth throttle. Add targeted limits for OAuth initiation/callback, refresh, and other abuse-sensitive unauthenticated routes.

### QA-S03 — Uploaded content type is trusted rather than sniffed

**Severity:** Medium

Upload completion verifies the stored object size but not its byte signature. A client can label arbitrary bytes as an allowed MIME type. Validate magic bytes for previewable/allowed formats and serve downloads with defensive content-disposition/content-type behavior.

### QA-S04 — Static web deployment has no explicit security headers

**Severity:** Low

`vercel.json` contains the build and SPA rewrite but no CSP, `Referrer-Policy`, clickjacking protection, MIME sniffing protection, or permissions policy. Public share tokens appear in URLs, making a strict referrer policy especially valuable.

### QA-S05 — Cross-site refresh requests can rotate a session

**Severity:** Low

The refresh endpoint relies on the cookie and does not enforce an Origin check or application-specific CSRF header. An attacker cannot read the credentialed response through CORS, but can cause unwanted token rotation/logouts.

### QA-S06 — Logout does not revoke an already issued access token

**Severity:** Low

Logout revokes refresh state, while an access JWT remains valid until its configured 15-minute expiry. This is common for stateless JWTs but should be explicitly accepted or mitigated for higher-confidentiality rooms.

### QA-S07 — Refresh-token records have no pruning mechanism

**Severity:** Low

Expired/revoked refresh-token rows accumulate indefinitely. Add scheduled pruning and an operational metric.

### QA-S08 — Dependency advisories remain open

**Severity:** Maintenance

The package audit reported:

- production graph: 18 advisories (0 critical, 5 high, 12 moderate, 1 low);
- full graph: 36 advisories (1 critical, 9 high, 23 moderate, 3 low).

Production advisories include `@nestjs/core`, `body-parser`, `file-type`, `lodash`, `multer`, `qs`, `react-router`, `react-router-dom`, and `uuid`. Existing review indicates several vulnerable code paths may be unused or unreachable, but versions should be upgraded or each exception documented with a reachability rationale.

## Recommended release sequence

1. Fix the two storage E2E selectors and reproduce the PDF viewer result with the official small fixture.
2. Resolve the refresh-replay and permissioned-revocation product decisions, then update specs/tests consistently.
3. Address or formally accept the medium security findings; add web security headers.
4. Deploy API and web, configure Google/storage/CORS/cookies, and run migrations.
5. Run all 44 E2E tests with `E2E_STORAGE_READY=true` against the deployed target, plus a manual real-Google sign-in/logout smoke test.
6. Add that deployed E2E suite as a required CI/release check.
